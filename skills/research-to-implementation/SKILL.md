# Research to Implementation

## Establish the mandate

Read the latest user instruction and current authoritative report, configuration, and project sources. Treat a request to implement previously proposed research as authorization for useful in-scope steps; do not preserve a superseded research-only restriction. Separate recommendation content from action authority.

Choose routine implementation details as the user's practical delegate. Preserve their objective, existing preferences, plan, budget, accounts, and privacy choices. Do not treat broad setup as permission to buy upgrades, send messages, widen sensitive access, publish, or accept binding terms.

## Review and choose

1. Extract concrete actions, dependencies, acceptance checks, and optional upgrades.
2. Verify uncertain consequential product claims using official sources and current tool capabilities. Confirm necessary account access with a harmless relevant read.
3. Inspect existing configuration before writing. Merge guidance without silently discarding current instructions. Prefer current authoritative files over remembered summaries.
4. Choose the smallest coherent setup. Reject obsolete, redundant, unsupported, and unnecessary recommendations; defer paid additions until a concrete gap justifies them.
5. Track each action in a compact ledger: recommendation; decision and reason; applied, prepared, blocked, deferred, rejected, or failed; actual evidence/check; next dependency. Record controlling decisions and label assumptions.

## Carry out the work

Use relevant research, decision, and execution workflows and supported specialist tools. Create current project context and execute available changes.

For recurring work, inspect existing tasks, run a useful manual pilot, verify required source access, and activate the authorized bounded schedule in the user's timezone. Make its prompt self-contained when future local-file access is uncertain.

Create or update reusable skills when requested or warranted. Follow skill-creator to initialize, validate, realistically test, install, and verify. Do not substitute a drafted file for a confirmed install.

Run proportionate checks on actual results. Use contrasting tasks to reveal regressions without pretending they are controlled model benchmarks. Never claim selected models, global settings, memory, model weights, or background activity changed without confirmed controls.

Continue independent work while sign-in or approval blocks one step. Prepare exact pending configuration before handing off. Seek the smallest necessary user intervention after concrete authorized work is complete.

## Document or record when requested

Discover an actual supported recorder before promising screen recording. Start capture before the taught steps. Exclude credentials, authentication entry, private sources, unrelated account information, and infrastructure secrets.

Capture real actions and preserve authentic outcomes, including corrected failures. Label the recording's scope and omitted steps. If continuous UI recording is unavailable, explain that limit and provide a supported terminal replay, captured-step walkthrough, or written guide. Never label reconstructed slides or screenshots as live recording.

Build the guide from observed actions and real results. Explain purpose, inputs, completion signal, common failure, and recovery. Separate completed demonstrations from pending account steps. Save requested recordings and guides using the environment's artifact-storage rules.

## Verify and hand off

Confirm applied configuration against the ledger, saved artifacts, recording playback/readability, and scheduling from returned task state. Keep prepared separate from applied.

Return the outcome first, installed skill names, artifact links, actual checks, and specific remaining blockers. Use the user's current platform for access directions. Retain a compact handoff and versioned evidence; make later permanent changes only within authorization.
