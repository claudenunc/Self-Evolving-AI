# Proposed direction — for discussion

Prepared 2026-10-03 from the user's vision. This is not an activated orchestration system or a commitment to build every component.

## Working model

The user describes the intended outcome and discusses meaningful choices with a coordinator. The coordinator chooses tools, delegates bounded work when useful, checks the assembled result, and preserves source code, decisions, handoffs, and teaching materials.

Use connected tools and repository code for structured operations. Use supported browser interaction for work that depends on a site's interface. Add a specialist AI when a concrete task benefits from it, with an explicit input/output contract and an independent result check. A chain of chats alone does not establish quality or durable context.

Project files provide continuity when they are read. Record concise supported facts, decisions, artifacts, unresolved questions, and next actions; keep private sources in an appropriate private location. Do not equate repository backup with complete or automatic model memory.

## Staged path

| Stage | Deliverable | Proof required before expanding |
| --- | --- | --- |
| 1. Preserve the foundation | Current project records plus archived research, workflows, and teaching media | Local and remote file integrity; usable links; clear privacy omissions |
| 2. Deliver one real project | A small useful app, service, or teaching product with explicit acceptance | It works for the intended user; effort, rework, and limits recorded |
| 3. Reuse a successful process | Tested workflow and relevant reusable skill/tool | Another task succeeds without copying hidden context or inventing outcomes |
| 4. Add a specialist provider | One bounded Claude/Gemini or other supported trial | Access confirmed; quality and effort improve enough to justify coordination |
| 5. Run focused discovery | A tested open-source scan tied to a real gap | Candidate provenance, license, dependencies, permissions, maintenance, and function checked |
| 6. Package a commercial offer | Deliverable, documentation, customer problem, and offer | Small demand test and credible delivery economics |

The valuable overlooked option is to sell a useful outcome before building a general-purpose orchestration platform. A specific customer problem gives the agents and tools a measurable job.

## First experiment

Choose one small project that can produce a useful finished result. Agree on inputs, audience, acceptance, $0 incremental spending, and publication scope. Run request → execution → verification → repository checkpoint → teaching guide. Record whether the user receives the result with less repeated explanation and correction. This tests the vision using the foundation already built.

## Current access and limits

GitHub write access is demonstrated for the named repository. The earlier setup confirmed ChatGPT Plus; this export does not establish current Claude/Gemini access. Cross-provider browser handoffs have not been tested. No background controller, new schedule, automatic skill installer, or paid infrastructure was created here.

[OpenAI's browser documentation](https://learn.chatgpt.com/docs/browser), opened 2026-10-03, supports signed-in Work browser tasks where rollout/account access permits them. It also describes separate browser sessions and sites that can block access. That supports a bounded trial, not a guarantee that another AI service accepts or completes every delegated task.

[OpenAI's scheduling documentation](https://learn.chatgpt.com/docs/automations), opened 2026-10-03, says web scheduled tasks can use accessible connected/uploaded context but do not keep local folders or worktrees between runs. Any future scanner needs a durable prompt, tested source access, defined destination, and stop/review rule.
